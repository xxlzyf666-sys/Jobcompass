# 真实模型诊断验收

当前工程测试使用虚构材料和模拟模型响应。真实 API 接入、真人报告质量和实际市场需求需要分别验证，不能用示例结果代替。

## 样本

收集 10—20 份获授权的后端开发简历及对应 JD。先移除不必要的姓名、联系方式和个人信息。覆盖 Go、Java 或 Python 服务开发，以及经历明确、经历简略、跨技术栈、JD 含加分项等情况。

## 每份报告的评估记录

| 项目 | 记录方式 |
|---|---|
| 模型与规则版本 | 记录实际模型标识、规则版本、测试日期 |
| 要求提取 | 是否漏掉必要项，是否添加 JD 没有的要求 |
| 要求分类 | 必要项与加分项是否分清 |
| 引用 | 自动校验应全部通过；人工检查是否断章取义 |
| 证据状态 | 是否把“关键词出现”误判成实践依据 |
| 事实保真 | 是否新增公司、项目、年限或业绩数字；发现即标记严重错误 |
| 建议具体度 | 是否指向一个具体段落和可回答的问题 |
| 用户采用 | 采用了哪些建议，拒绝了哪些，为什么 |
| 失败处理 | 模型拒绝、超时或校验失败时，用户是否知道下一步 |

与直接使用通用 AI 的结果匿名对照，不先告诉评估者来源。记录偏好与原因，不把少量“看起来有用”的反馈当成确定需求。

## 上线前的决策

新增求职准备功能需要对同一批真实授权样本继续检查：

| 功能 | 验收重点 |
|---|---|
| 追问 | 是否指向具体经历；是否避免诱导用户提供不存在的指标 |
| 逐段精修 | 改写是否更清楚；是否改变职责边界、凭空强化因果或引入原文和确认事实以外的内容 |
| 岗位版本 | 不同 JD 的内容重点是否有实际差异，同时保持经历一致 |
| 事实纠正 | 用户更正或删除事实后，后续生成是否采用最新版本 |
| 面试提问 | 是否基于该次简历快照和真实回答追问，是否重复、泛化或难度失配 |
| 逐题反馈 | 引用是否真实，评价是否对应回答，提纲是否将技术建议冒充用户做过的工作 |
| 复盘与再练 | 改进项是否可执行，新一轮是否针对上一轮薄弱点 |
| 实际采用 | 用户最终使用了哪个版本、采纳了哪些改写，是否愿意再次练习并实际付费 |

采纳次数和练习次数是使用信号，不能直接推断录用效果。

- 有未经确认的新事实、虚假引文或越权访问：先修复，再增加样本。
- 引文正确但建议空泛：检查所选岗位范围、规则及输入完整性。
- 多数建议被实际采用：继续小范围开放，收集失败案例。
- 不保证面试、录用或薪资结果；报告只帮助用户把已有事实表达清楚。
